# ADR-0003: 高级 RAG 检索管线——混合检索与 Cross-Encoder 重排

- Status: Accepted
- Date: 2026-10-19（commit `684393c`：拆分数据管线与检索策略）
- Related:
  - 代码：`src/rag/strategies/`（retrievers / fusers / hybrid / rewriters）、`src/rag/reranker.py`
  - 配置：`src/rag/retrieval.py`（检索管线编排）

## Context

在构建 RAG 系统时，如果仅仅使用向量检索（Dense Retrieval），会遇到常见的业务瓶颈：
1. **词汇鸿沟**：向量模型对专有名词、产品型号、特定缩写的召回效果极差（比如用户搜“V2.0 部署”，向量可能会召回一堆“版本发布”的文档，但漏掉精准的“V2.0”）。
2. **上下文冗余**：通过简单向量相似度拉回来的 Top-K 文档，往往存在大量冗余片段，真正回答问题的核心段落可能排在 10 名开外，直接喂给大模型会导致“Lost in the Middle”现象。

如果只是“调个 API 拼 Prompt”的 Demo，只用向量检索足矣；但作为“企业级”项目，必须保证极高的召回率和准确率。

## Decision

构建**多级漏斗式的 Advanced RAG 检索管线**：

1. **多路召回（Hybrid Retrieval）**：同时执行向量召回（捕捉语义）和 BM25 关键词召回（捕捉精确词汇）。
2. **融合策略（Fusion）**：将两路召回的结果通过 RRF（Reciprocal Rank Fusion）或加权分数进行合并。
3. **查询改写（Query Rewriting）**：在检索前，利用小模型对用户的原始 Query 进行扩展或拆解（HyDE / 多查询扩展）。
4. **重排（Reranking）**：对融合后的 Top-N 文档（如 N=20），使用 Cross-Encoder（如 BGE-Reranker）进行深度的交互式计算，选出真正的 Top-K（如 K=5）。
5. **策略化装配**：通过 `strategies/` 目录下的工厂模式，允许业务层按用例选择管线（如快速对话直走向量，深度问答走完整混合+重排）。

## Alternatives Considered

- **A. 纯向量检索（Dense Only）**：**否决**。在企业级长文档和专业术语场景下，召回率完全不达标。
- **B. 纯关键词检索（BM25 Only）**：**否决**。无法理解同义词和用户的自然语言表述。
- **C. 向量 + BM25 线性拼接（不用重排）**：**否决**。线性融合的分数在很多时候并不对齐，真正的强相关文档依然可能排在第 8、第 9 位，影响 LLM 的发挥。
- **D. 使用大模型直接读长上下文（如 128k 模型，直接塞全量文档）**：**否决**。成本极高，且推理延迟无法接受，更无法满足多租户并发。

## Consequences

**正面**
- **极致的召回与精度**：BM25 保下限（字面匹配绝不出错），Cross-Encoder 拔上限（深度判断语义相关性）。
- **灵活性极高**：通过 `ab_test` 中的 `STRATEGIES` 配置，可以随时调整（如 `fast` 策略省掉重排，`safe` 策略加上 LLM 审核）。
- **模块彻底解耦**：`retrievers`、`fusers`、`rewriters` 被拆分为独立组件，可以随时替换（如将 BM25 换成 ES 的检索）。

**负面（接受的代价）**
- **极速恶化**：Cross-Encoder 重排极其消耗算力，引入后单次 RAG 检索延迟会增加数百毫秒。
- **系统复杂度爆炸**：管线的环节越多，排查 Bug 越难。如果用户反馈“没搜到答案”，你需要依次排查：改写写对了吗？向量召回满了吗？BM25 召回了啥？融合后去哪了？重排怎么打分的？
- **模型加载成本**：必须加载额外的 Reranker 模型（可能占用显存/内存）。

**备注：企业级的下限**
正如开发者所言，成熟的 RAG 不是“跑通就行”，而是“多路兜底”。这套管线的价值在于，即使向量模型拉垮了，BM25 也能把它拉回来；即使召回了一堆废话，Reranker 也能把真正有用的那一段按回前五名。
